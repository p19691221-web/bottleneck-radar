# AI 瓶頸雷達

AI 讓產出、建議和操作變得便宜之後，哪種配套先塞車？這個網站收集有來源、標明證據強度的訊號，分成六種瓶頸：審查與查證、授權與範圍、協調與容量、偵測與事故證據、信任與正當性、實體與資源。

純靜態網頁，資料全部放在這個 repo 的 GitHub Issues，架構與小軟體收藏館相同：

- **回報**：訪客用 issue 表單回報，自動加上 `signal` 標籤。表單要求附來源網址，並提醒用自己的話描述、不貼原文。
- **核實與上架**：整理者確認來源存在後，加上 `listed` 和三類標籤，訊號就會出現在網站上。拿掉 `listed` 或關閉 issue 即下架。
- **討論**：每則訊號的 issue 就是它的討論區，網站上可直接閱讀。
- **我也看到**：issue 上的 👍 數會顯示在卡片上。
- **我能解這個**：每張卡片有「我能解這個」連結，打開預填好訊號編號的 `offer.yml` 表單，自動加上 `offer` 標籤。回應者要填能解哪一段、能力證據網址與公開聯絡方式。

## 只有整理者能設定的三類標籤

回報者在表單裡選的瓶頸只是建議，網站不會採用；瓶頸、證據強度與訊號類型都只讀整理者設定的標籤，回報者無法替自己的訊號分類或標證據強度。

| 標籤 | 選項 |
|---|---|
| `瓶頸:` | 審查與查證、授權與範圍、協調與容量、偵測與事故證據、信任與正當性、實體與資源 |
| `證據:` | 原始紀錄、當事方聲明、媒體轉述 |
| `類型:` | 已有人付出成本、塞車跡象、平台吸收、治理先行、歷史先例 |

沒有標籤的欄位，網站會顯示「未分類」、「證據未標」或「類型未標」，不會從表單或其他欄位補值。

## 設定步驟

1. 在 GitHub 建立公開 repo，名稱 `bottleneck-radar`（帳號 `p19691221-web`）。若用別的名稱，改 `index.html` 裡的 `OWNER` / `REPO`，以及執行種子腳本時的 `REPO`。
2. 上傳本資料夾所有檔案，包含 `.github/ISSUE_TEMPLATE/` 和 `scripts/`。
3. Settings → Pages → Source 選 `Deploy from a branch`，Branch 選 `main` / `(root)`。
4. 在 Codespaces（或任何已登入 `gh` 的環境）於 repo 根目錄執行一次：

   ```
   ./scripts/seed.sh
   ```

   它會建立 `signal`、`listed` 與三類標籤，並建立第一批 13 則已核實的訊號（含 2 則歷史先例）。只執行一次；重跑會產生重複的 issue。
5. 網站網址：https://p19691221-web.github.io/bottleneck-radar/

## 核實一則新回報

1. 打開來源網址，確認內容存在且與描述相符；描述若引用原文，請改寫成摘要。
2. 依來源性質加 `證據:` 標籤：一手文件為原始紀錄，涉事方自己的說法為當事方聲明，其餘為媒體轉述。
3. 加 `瓶頸:` 與 `類型:` 標籤，最後加 `listed`。

上架只代表來源存在並已分類，不是對事件的判定。

## 核實一則「我能解這個」回應

1. 確認「對應訊號」是已上架訊號的編號（`12`、`#12` 或 issue 網址都可以）；不對就直接改 issue 內文。
2. 打開能力證據網址，確認存在且與「能解什麼」相關。
3. 加上 `listed`，回應就會出現在那則訊號的卡片與詳情裡。拿掉 `listed` 或關閉即下架。

顯示只代表證據連結存在，不代表能力已驗證，也不是推薦。對應訊號下架時，回應不會顯示。

若 repo 是在加入此功能前建立的，只需補建一次標籤：

```
gh label create offer --repo p19691221-web/bottleneck-radar --color c27a0e --description '我能解這個：針對訊號的解法回應'
```

## 限制

- 回報與討論需要 GitHub 帳號。
- 網站讀取 GitHub API 不需登入，但同一網路每小時上限 60 次；頁面會快取 5 分鐘。
- 已上架訊號與回應共用一次讀取，合計最多 100 則。超過時需要加分頁。
- 雷達上的數字是已上架訊號的筆數，不是事件發生頻率。
